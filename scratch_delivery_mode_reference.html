Accepted values

Are the valid values in_person, online, and hybrid?

That's the documented convention, but it is not enforced. DeliveryMode = str in event_schema.py:11 is a bare type alias, not an Enum/Literal — Pydantic accepts any string, including typos, for both create and update.

The one piece of mode-aware logic that exists

This is the entire delivery_mode-related logic in the backend — nothing else references it.
def _auto_meeting_link(delivery_mode, provider, existing):
    if existing:
        return existing
    if delivery_mode in ("online", "hybrid") and provider:
        # generates a fake zoom / meet / teams link
        return f"https://zoom.us/j/{...}"  # etc, provider-dependent
    return existing  # i.e. still null if provider wasn't set

05

Form-configuration publish — no cross-field guard

Publish validation (validate_sections_for_publish) only force-keeps five fields enabled: title, description, category, start_date, end_date. delivery_mode, venue, location_id, meeting_link, meeting_provider are not in that set.

Consequence: a Super Admin can publish a config where delivery_mode offers "Online" as a choice while meeting_link and meeting_provider are both hidden from the same form. Nothing blocks that publish, and nothing catches it at event-create time either.

06

Does the registry expose delivery_mode's options?

partially — the registry entry itself (FIELD_REGISTRY) carries no options list. The three values only appear if a config is built from build_default_sections()'s hardcoded template. A config built from scratch has no registry-level constraint on what options get attached to delivery_mode — could be anything, or nothing.

07

Can Super Admin disable a field the backend "needs"?

yes, freely — venue has removable: false (can't delete it from the registry) but hideable: true. Since none of the location/meeting fields are domain-required (see §05), any of them can be set is_enabled: false in a published config with no warning, no matter what delivery_mode options are offered alongside it.

What this means for the client

The backend will not stop you from saving invalid combinations — so the form has to.
  1. Validate delivery_mode client-side against a fixed enumBackend accepts any string — don't rely on a 422 to catch a bad value.
  2. Make venue/location required in the UI when in_person or hybrid is selectedBackend will silently save nulls otherwise.
  3. Make meeting_link or meeting_provider required in the UI when online or hybrid is selectedOnly meeting_provider triggers an auto-generated fake link — that's a dev convenience, not something to depend on in production forms.
  4. Don't assume the active form config's field set matches delivery_mode's needsA Super Admin can hide venue/meeting fields independently of which delivery_mode options are shown — check what's actually enabled before deciding what's required.
  5. Treat auto-generated meeting links as placeholders, not real oneszoom/meet/teams links from _auto_meeting_link are randomly generated stand-ins, not live meetings.
